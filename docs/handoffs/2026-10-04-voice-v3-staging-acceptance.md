# Voice v3: controlled Staging acceptance protocol

This is a proposed financial acceptance protocol. It is not authorization to enable automatic posting or run its first financial capture. Production, integration into the final branch and public release remain outside this continuation.

## Candidate prerequisites

Pin the candidate SHA, successful full exact-SHA workflow (including k6), immutable image digest and additive migration checksum in the external release evidence. Independently review the delta from `3976774`. Complete bilingual ten-event non-posting provider checks and an eleven-event overflow rejection with ledger snapshots and reconciled provider receipts. Preserve the 1,200-token cap, global USD 2 budget, existing unknown-cost holds, Vertex global/ZDR route, M4A and capture limits.

Hosted Staging currently has no v3 batch/policy tables; no migration or deployment has been performed by this continuation. Before financial approval, prepare and validate a controlled Staging migration/deployment with the policy disabled, using the exact tested image and migrations, then inspect owner-qualified constraints, function grants, checksums and security advisors. Repeat the non-posting accounting/financial checks if the deployed transport changes. Do not auto-confirm legacy proposals. Onboarding and existing v2 operations retain their current contract.

The inherited deep-link decoder availability exposure is documented separately. It must have a compatible mitigation and regression before public release; dependency audit findings are not waived by green Voice CI. Synthetic speech proves capacity, not real human financial accuracy. Samsung timing and speech acceptance remain outstanding.

## Explicit financial-canary approval boundary

Request approval naming the exact SHA/image/migrations, fictional Staging owner, enabled policy scope, maximum captures, reservation/cost allowance and rollback. If the policy cannot be owner-scoped, restrict authenticated Staging access and stop unrelated work before enabling it. Record a baseline of owned transactions, postings, balances, ledger versions and active Voice work. Never alter unrelated owners, existing unknown-cost reservations or Production.

Start with **one English human Samsung recording containing ten explicit supported events**, with consented fictional data and active test taxonomy/accounts. Use cash as the default, SAR with two minor units and capture-local date in Asia/Riyadh. Story: cash breakfast 25; cash taxi 40; card groceries 120; cash lunch 30; card pharmacy 65; card phone bill 80; cash books 45; card household items 55; cash parking 10; cash salary received 5,000. Name the active categories/accounts explicitly where needed. Resolve test fixtures before speaking; never fix an unsafe result by changing its identity or replaying audio automatically.

Expected: ten distinct transaction cards, nine expenses and one income, zero Review/Save/Confirm/needs-details UI. Expense total is SAR 470. Cash net increases by SAR 4,850 (485,000 minor units); card net decreases by SAR 320 (32,000 minor units). Combined delta is SAR 4,530 (453,000 minor units). Verify receipts, signed postings, revisions/audit/outbox and normal Home/history reload against authoritative server data. No inferred exchange conversion. Require exact event agreement, not merely a ten-count result. Stop on any unexpected financial field, duplicate, missing occurrence or balance discrepancy.

Cancel or disable remaining automatic work at the first discrepancy. Already committed transactions remain and must be corrected through ordinary audited transaction management; do not erase ledger evidence, rerun inference or turn skipped events into drafts. Turning the gate off must preserve receipts and prevent new uncommitted execution according to the approved rollback policy.

## Subsequent bounded acceptance, after first canary passes

1. Arabic human ten-event equivalent: compare every amount/account/category/date/currency and ten independent identities. Cross-check English/Arabic counts and balances. Keep each recording under 60 seconds.
2. Mixed four-event story: breakfast SAR 25 cash, taxi SAR 40 cash, household items SAR 120 card, friend returns SAR 50 previously lent. Expect exactly three cards; unsupported repayment creates no transaction, draft, prompt, posting or balance effect. Include a separate missing-amount case and explicit ambiguous account/date; valid siblings still commit, unsafe fields never default. Zero-safe story displays only “No transactions were added.”
3. Exactly-once/recovery: replay the same create/process identities and duplicate finalization deliveries through a controlled fault harness. Drop a result response after commit, restart/recover and prove receipts reconcile without another inference or financial effect. A genuinely new identical recording is a distinct occurrence and creates new IDs. Infrastructure failures remain pending/failed, never semantic skips.
4. Cancellation: before handoff deletes capture; after handoff cancels remaining execution. Race against finalization and verify acknowledged cancellation or one receipt per item. Committed siblings remain visible. Offline cancel stays pending until acknowledgment. Navigation/new recording never implicitly cancels accepted work.
5. Samsung repeated recordings: instrument Tap→guard→permission→audio mode→native prepare→Recording and Stop→native completion→release→durable SQLite handoff→Ready. Start capture B while A is still analyzing; repeat while A recovers or connection is absent. Require Ready within 250 ms after native release plus durable handoff, no extra tap and no dependency on Gemini, server cleanup or earlier batches. Measure native preparation separately. No arbitrary sleeps. Exercise backgrounding, app termination and owner change; stale callbacks must not affect a newer capture.
6. Privacy/accounting: inspect minimal skipped operational rows, removed unexecuted commands, public result fields and safe logs/export. No skipped amounts, raw model response/transcript, reasoning or sensitive account labels. Verify one provider receipt per actual dispatch, bounded retries, media purge/tombstones and unchanged unknown-cost holds. Confirm cross-owner API/RBAC rejection without provider or ledger effect.

Record actual dispatches and cumulative spend after each gate. Do not run all captures blindly: stop after any failure and investigate without increasing quota, retries or budgets. Public release additionally requires compatible Mobile security remediation and completed physical acceptance. This protocol does not authorize branch integration or Production.
