# رسائل الآيفون — تنفيذ المصدر وحدود قبول الجهاز

## الحالة

لم يُثبت التفعيل المالي على الآيفون بعد. أضيف مستقبل Shortcuts فعلي في المصدر مع التقاط مساعد ومراجعة، لكنه غير موجود في التطبيق المثبت. لا تُعد شاشة الإعداد أو اختبار Jest أو وجود مشغّل الرسائل دليلًا على وصول رسالة إلى حساب مالي على الجهاز.

التعديل داخل `E:\Masarifi-iOS` على فرع `iOS` ابتداءً من `d62bfe0e2c59d000225055041c15f14ab10c0d97`. بقي stash `ff79cf20f821725ec5a8f909c2760822d53a50c7` موجودًا. لم تُعدّل هوية Android أو ملفاته الأصلية أو EAS أو Firebase أو API أو قاعدة الإنتاج. لا بناء IPA أو OTA أو رفع Apple.

## ما تغيّر

- مستقبل iOS خاص للرابط المحلي `masarifi://capture-ios?payload=...`، يفصل مدخل الرسالة عن التنقل ويزيل الحمولة من وجهة Expo قبل عرضها. روابط SSO والـlauncher محفوظة.
- سماح محلي مرتبط بمالك التطبيق وجلسة Clerk، محفوظ في SecureStore؛ لا يقبل owner/account/amount من الرابط. لا يُرسل النص أو OTP إلى API. يحتفظ مؤقتًا بحقول مالية مشتقة فقط ولا يسجل النص أو الرابط.
- محلل المشروع المعتمد يحدد شراء/رسوم أو راتبًا مكتملًا؛ المدخل غير المالي والرموز والفشل والانتظار والتحويل والاسترداد غير المدعوم تُرفض محليًا. يختار المالك حسابًا نشطًا مملوكًا له بالعملة الصحيحة ومفعّل التتبع.
- تأكيد داخل التطبيق ثم الطابور المعتمد `SmsImportQueue` ثم استيراد v1 المساعد (`sourceType: manual`, `sourceChannel: ios_shortcut`) عبر هوية الخادم وحاجز الجيل المالي. لا تُزوّر أدلة Android/v3 ولا يُغيّر وضع التتبع العام من إعداد الآيفون.
- مفتاح إعادة المحاولة ثابت من هوية الالتقاط والمرسل والتاريخ والمحتوى. إعادة الحمولة نفسها لا تنشئ أمرًا جديدًا؛ الهوية المختلفة لا تُحذف لمجرد تشابه المبلغ والنص. تبقى مراجعة التكرار على الخادم مطبقة. إذا لم يوفر Shortcuts معرّف الرسالة الأصلي، يُولّد UUID مرة واحدة للالتقاط ويُعاد استخدام القاموس نفسه عند المحاولة؛ تشغيل الأتمتة من جديد ليس إثباتًا لإعادة تسليم الرسالة الأصلية.
- لا تظهر «حُفظ» إلا مع إيصال خدمة يحتوي عملية مقبولة ومعرّفها؛ انتهاء الطلب وحده لا يكفي. يوجد مدخل iOS إلى شاشات المراجعة وحسم التكرار المعتمدة. لا يلزم تعديل مسار Android للوصول إليها.
- التأكيد اليدوي الخاص بـiOS يعمل حتى عندما يكون الالتقاط التلقائي العام متوقفًا؛ لا يغيّر تفضيلات Android. تُحمّل مراجعات iOS المعلّقة بكل صفحاتها ويُفرّق حسم «الاحتفاظ بالموجود» عن الفشل أو حفظ عملية جديدة.
- فحص موافقة الالتقاط هو آخر فحص غير متزامن قبل إرسال HTTP. تُحفظ إيصالات الطلبات التي أُرسلت فعلًا عند انتقال التطبيق للخلفية، مع استمرار حواجز المالك والجلسة والجيل المالي؛ لا تملك كتابة الإيصال صلاحية إعادة تفعيل الموافقة.
- لإزالة البيانات ثلاثة مداخل مغطاة: حذف بيانات الجهاز من إعدادات الخصوصية، والخروج مع إزالة البيانات، واكتمال حذف الحساب. يمسح كل منها سجلات Shortcuts المطابقة للمالك فقط عبر قفل كتابة مشترك، حتى بعد تشغيل بارد لم يحمل المستقبل. إعادة الضبط المالي تمسح إيصال العملية والمدخل المؤقت وتحفظ موافقة الجلسة. لا يُعاد إرسال عمل أزالته مصالحة الجيل المالي.

## تحقق الجهاز بتاريخ 16 نوفمبر 2026، بتوقيت الرياض

قرأ استعلام مقصور على التطبيق: bundle `com.masarifi.mobile`, version `1.0.0`, build `10`. مصدر هذا البناء بحسب manifest الاستلام هو `5b5d3c7976c0d6351ae895012bbf43b847260aff`، وليس المصدر الجديد. لم يُستبدل التطبيق.

فُتح تطبيق Shortcuts الرسمي. ظهرت شاشة iOS 27 التي تشرح Unified Automations، ثم `Edit → Automation → Message`. مشغّل `When I receive a message` موجود فعليًا، ويعرض `Configure “Sender” to enable this automation`. لم يُحدّد مرسل بنكي أو شخصي ولم يُفعّل التقاط كل الرسائل. كانت `Privacy → Allow Running When Locked` مفعّلة افتراضيًا للمسودة؛ لم نغيّرها. وجودها لا يثبت أن إجراء Open URLs أو التطبيق يستطيع إكمال الحفظ أثناء القفل.

عارض الشاشة توقف وعاد مرات متعددة (قرابة 4–7 ثوانٍ في سجله). لا يُستعمل زمن الشاشة أو الطلبات لقياس Face ID. الصوت في المتصفح لم يُفعّل، والـclipboard sync بقي متوقفًا. لم يُفتح أرشيف Messages أو يُرسل SMS/تقرير/سؤال AI أو يُقرأ تخزين التطبيق الخاص.

## مصادر Apple والبدائل

- [إضافة الأتمتة في iOS 27](https://support.apple.com/en-om/guide/shortcuts/apdfbdbd7123/10.0/ios/27): إنشاء المشغّل من داخل الاختصار والسماح بالتشغيل أثناء القفل. معاينة الجهاز تؤكد الواجهة الجديدة؛ ليس تبويب الأتمتة القديم وحده هو المسار.
- [التشغيل دون سؤال](https://support.apple.com/guide/shortcuts/enable-or-disable-a-personal-automation-apd602971e63/ios): Message ضمن المشغّلات القابلة للتشغيل آليًا، مع احتمال إعداد إجراءات منفردة.
- [سياسة مصادقة App Intent](https://developer.apple.com/documentation/appintents/appintent/authenticationpolicy): إعداد مستقل عن تشغيل تطبيق React Native. إضافة Intent أصلي لم تُنفّذ في هذه الدفعة؛ تحتاج بناءً أصليًا وتصميم خلفية مصادقًا عليه.
- [IdentityLookup](https://developer.apple.com/documentation/identitylookup/sms-and-mms-message-filtering): تصفية محدودة لمرسلين مجهولين، وليست قراءة صندوق جميع الرسائل؛ لا تصلح قناة عامة لإثبات تتبع مالي كامل.
- [TelephonyMessagingKit](https://developer.apple.com/documentation/TelephonyMessagingKit): يتطلب Default Carrier Messaging App entitlement وحسابًا وموقعًا داخل الاتحاد الأوروبي. لم يُطلب هذا الاستحقاق ولم نفترض أهلية الهاتف أو ننفذ قدرة Apple جديدة.

إرسال Shortcuts مباشرة إلى API ليس بديلًا جاهزًا في النسخة 10: المسار المعتمد يحتاج هوية مالك مصادقًا عليها وحاجز الجيل المالي. لم نستخرج bearer token من التطبيق أو ننشئ مفتاحًا طويل الأجل أو نضع بيانات الدخول في الاختصار لتجاوز المستقبل المفقود.

## ما يلزم للمتابعة

اكتمل تأهيل المصدر. تبقى معالجة قيد المالك «حل بياض Face ID قبل بناء نسخة جديدة». لا يُعد طلب التركيز على الرسائل إلغاءً لهذا القيد. الخيار العملي لاختبار المستقبل على هذا الهاتف هو نسخة AdHoc موحدة واحدة من المصدر المؤهل بعد معالجة القيد أو استثناء صريح منه؛ لا TestFlight أو OTA أو نشر تلقائي. ملف البناء الحالي `ios-ad-hoc` محفوظ دون تغيير؛ إن أُجيز البناء، تُستخدم الهوية وبيانات التوقيع القائمة مع `--freeze-credentials`، ومن دون شراء أو ترقية أو تعديل شهادات أو رفع Apple.

بعد توفرها: إعداد السماح للجلسة، اختصار QA بنص وهمي ومعرّف/توقيت ثابتين، نقل القاموس إلى المستقبل، اختيار حساب QA، تأكيد ثم معاينة إيصال العملية ورصيد الحساب. إعادة نفس القاموس تثبت عدم التكرار، ثم هوية جديدة متشابهة مع مراجعة التكرار. اختبار الرسالة الواردة يتطلب خطوة إرسال المالك إلى هاتفه ببيانات وهمية فقط. بعدها بقية Face ID/RTL والمالي والصوت والإشعارات وفق الاستلام، دون إعادة إرسال التقرير السابق.

نجحت اختبارات API المحلية ذات الصلة: 5 مجموعات / 49 اختبارًا (DTO والاستيراد والعامل والمراجعة والتكرار). قبل محقّق API الحقيقي الأمر المصغّر للآيفون دون نص/مرسل/مالك من العميل. نجحت فحوص config/production: 34/34؛ وحفظ هوية Android: 35/35 مع الفحص الفعلي. نجح frontend-quality وESLint للنطاق وTypeScript على المصدر النهائي المصحّح. فحص Gitleaks للإضافات المرحّلة، بما فيها أدلة الجهاز، نظيف دون إضافة استثناءات. كان تنبيه الفحص الأول على اسم ثابت مسار SecureStore غير السري؛ حُسّن اسم المتغير دون تغيير عنوان التخزين أو إضافة تجاهل.
