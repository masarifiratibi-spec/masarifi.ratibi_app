## الحالة التي لا تُعاد

نقل PostgreSQL والملفات **مكتمل**: الهدف قبل الكتابة منذ13نوفمبر16:15:51UTC، والحالة الدائمة `phase=complete` و`targetMayAcceptWrites=true`. طابقت199جدولًا و5sequences و177migration والملفات الأصلية. آخر فحص API عام في14نوفمبر07:42:57UTC أعاد200 وready مع database=up وqueue=up؛ لا يساوي ذلك حصرًا جديدًا للحاويات.

VPS هو `187.77.81.97`، Hostinger `2006836`. القاعدة `masarifi-postgres17` وبياناتها `/srv/masarifi/postgresql17`؛ الملفات `masarifi-private-storage` وبياناتها `/srv/masarifi/files`. التشغيل المؤهل `/opt/masarifi/selfhost/releases/2026-11-13`، والحالة `/etc/masarifi/selfhost/cutover-state.json`. آخر حصر موثق30حاوية هدف عاملة، و50مستهلكًا قديمًا متوقفًا مع restart=no. التخزين أُصلح healthcheck الخاص به وأصبح healthy.

الإصلاح يكون إلى الأمام على VPS. أبقِ المستهلكين القدامى متوقفين، ولا تعاود أدوات cutover/complete أو حزمة نوفمبر7 أو rollback إلى Supabase. كود الفرع ليس تصريحًا لاستبدال runtimes الخادم المؤهلة بـcheckout كامل. Clerk باقٍ للمصادقة وSQLite باقية للموبايل.

## المطلوب، بالترتيب

1. **الحالة الفعلية:** اقرأ الحالة الدائمة وجاهزية API والتخزين وسجلات نافذة محدودة وفق runbook. الوصول الذي نجح سابقًا هو Hostinger Web Console؛ SSH22 انتهى بمهلة، والتبويبات القديمة ليست ضمانًا للوصول. لا تطبع Env أو أسرارًا أو connection strings. تنتهي الخطوة بتحديد عطل حالي بدليل أو تسجيل أن الفحص المحدد سليم.
2. **العمال والعقود:** راجع مسارات مزامنة الموبايل، وvoice contracts، والتقارير والمساعد مقابل نطاقات العمال الفعلية على الهدف. fixtures المساعد والمزامنة عالجها العمال المعتادون؛ fixtures تقرير التنزيل وvoice contract2 استُخدم لها محرك الهدف تحت أقفال IDs محددة. المطلوب إثبات التقاط طوابير legacy تلقائيًا إن كانت ضمن الاستخدام، مع الحفاظ على قيود المالك والـepoch/provider/job. لا توسّع نطاق عامل لمجرد جعل fixture يمر.
3. **التتبع الفعلي:** ما زال التقاط SMS/إشعار مالي حقيقي غير مثبت. جهّز المراقبة والتشخيص أولًا، ثم اطلب من المستخدم الإذن/الإدخال اللازم فقط. يفعّل المستخدم أذونات Android بنفسه؛ لا تمنحها تلقائيًا أو ترسل SMS/إشعارًا تجريبيًا إلى آخرين. القبول يربط الرسالة أو الإشعار بمعاملة المالك المقصود، والمراجعة عند الغموض، والمزامنة مرة واحدة دون تكرار.
4. **الصوت الفعلي:** جهّز اختبارًا ببيانات يختارها المستخدم، مع احترام الموافقة الصوتية القائمة. أثبت اكتمال التسجيل والتحليل والمراجعة/التسجيل المقصود والمزامنة، واربط requestId وoperationId والـjob دون نشر النصوص أو الصوت أو محتوى مالي خاص. أصلح الفشل المثبت وأعد اختبار مساره فقط.
5. **دورة التقرير:** اختبار renderer/SMTP الاصطناعي إلى بريد المشروع نجح ووُثق. دورة التطبيق الكاملة لم تُقبل: المحاولة `47c05bf5-2353-4f63-acb3-4ac5d0afc2b3` وصلت delivered لكن مستلمها لم يطابق البريد المطلوب. المستخدم يفتح التطبيق بحساب `masarifi.ratibi@gmail.com` دون مسح بيانات الحساب الحالي؛ أثبت البريد الكامل من الهوية قبل أي طلب تقرير. جهّز النتيجة والمستلم للمراجعة واحصل على تفويض الإرسال المحدد قبل الإرسال. لا تكرر المحاولة القديمة أو تغيّر مستلم حساب آخر. القبول يتطلب API وstorage وworker وPDF صحيحًا ووصوله للمستلم الصحيح؛ حالة delivered وحدها غير كافية.
6. **إغلاق المتبقي:** سجّل نتيجة كل مسار وحدوده، وأصلح الأعطال المثبتة في المصدر مع فحوص مناسبة. إن احتاج إصلاح نشرًا على VPS، جهّز payload محددًا ومؤهلًا مطابقًا لإعدادات التشغيل الفعلية قبل أي موافقة لازمة. جهّز مرجع مصدر قابلًا لإعادة الإنتاج للحزمة المقبلة؛ نشر المتجر وتغيير سياسة التحديث والحملات ورفع وثائق الهوية ليست ضمن هذا التفويض.

لا يلزم تكرار قبول offline السابق: المعاملة حُفظت pending محليًا ثم أصبحت صفًا واحدًا بعد الاتصال، وبقيت واحدة بعد التحديث وإعادة الفتح. لا يلزم تكرار اختبارات نقل البيانات أو بناء الهاتف لمجرد فتح الشات. إذا لم يظهر عطل فلا تختلق مرحلة نقل جديدة؛ أتمم بند القبول المحدد أو بيّن مدخل المستخدم المطلوب مع استمرار العمل المستقل.
