## Decisions and behavior

- Overview values come from the response, including 0, 12 and 1234. Missing billing and HTTP-error telemetry stays null/unavailable, with unavailable regions rather than invented charts. Plan labels use the actual plan key; paid share uses actual counts.
- Registered profiles, new profiles in the reporting range, overlapping native-platform populations, unknown-platform users, registered devices and app versions come from stored records. Device presence is never an activity signal. Version distributions retain all devices with at most 24 individually named versions plus an other-versions group per OS.
- Import, AI and support sources have no reliable originating OS. Their real counts and import trend are explicitly global, including under an OS filter. Admin-support AI traffic is excluded.
- Native startup/foreground records one authenticated user/platform observation per UTC 15-minute bucket. The endpoint accepts only platform, refuses browser Origin, and requires an active profile and an owned, unrevoked native device bound to the authenticated Clerk session. The mobile helper captures/rechecks identity around registration and delivery. No content, screen names, device identifiers or client timestamps are stored in the activity table.
- Collection starts at migration execution, with no historical backfill. Reports return collection start, database observation time, reporting boundaries and timezone. Daily users are distinct users per configured reporting day; monthly users use a rolling 30 reporting days. Dates before collection have null points, and incomplete activity history is marked partial. Multiple devices and overlapping platforms deduplicate by user for totals. Retention is 120 days, enforced from the existing report-expiration worker polling path; profile deletion cascades observations.
- Support financial reports retain support-grant checks and use canonical confirmed, undeleted transaction effects with exact local start-inclusive/end-exclusive bounds. Snapshot/PDF currency follows currency_code and the currency catalog minor-unit scale, including mixed currencies. Existing public/mobile report response contracts remain unchanged.
- Overview, platform analytics and activity CSV exports capture actual dataset rows with dataset-specific columns and formula neutralization. Snapshot metadata retains observation boundaries. Audit mapping uses emitted security action names and distinguishes deletion requested/cancelled from completed records; includes role changes and support decisions.

## Fix round 1 — four review findings

Review base: `5f921f909e1f9f24e11cebd66dbcab6f6c32abc6`. Read the full `task-1-review.md`; all four P2 findings were reproduced and addressed. This round changes API/report code and an additive SQL migration only; Admin and Mobile source remain unchanged.

1. **Endpoint contract:** `recordMobileActivity` is now the stable operation ID with `ApiBearerAuth('ClerkBearer')`, retaining the existing Clerk guard. The approved reports OpenAPI fragment supplies the required strict platform-only object, ios/android enum, bearer security, 204 empty success and safe 400/401/403/429/503 errors. The existing fragment composer and drift gate validate it. HTTP validation also rejects array-coerced platform values rather than treating `['ios']` as the string `ios`.
2. **Export completeness:** overview/analytics rows retain each metric or series' freshness, timezone, periodStart, periodEnd and collectionStartedAt alongside observedAt. CSV exposes those columns. Active-customer rows use activity freshness rather than registration freshness; monthly series retain their partial state. Snapshot dataState now considers partial/unavailable/stale measurement state as well as null values. The explicit seven-day-after-fourteen-days-of-collection regression has numeric monthly values and still exports partial, qualified rows.
3. **Stable activity observation:** the service delegates to `ReportsRepository.getAdminActivityExport`. One repeatable-read transaction captures measurements and then fetches at most 10,001 rows from new permission-checked `read_admin_overview_activity_at(text,integer,integer,timestamptz)` using that exact observed-through instant for both reporting-day boundaries and event upper bounds. Over 10,000 rows fail explicitly; mutable offset paging was removed from exports. Existing paginated UI reads remain unchanged. Activity CSV also includes stable IDs. The real DB test inserts a new leading audit event from a separate connection between the observation and bounded activity fetch, then verifies its exclusion, every original ID exactly once, unique IDs and the temporal upper bound.
4. **Customer-local support dates:** the repository receives the captured instant and relative day count, rather than UTC-derived dates. New grant-checked `read_supported_financial_report_relative(text,integer,timestamptz)` resolves the authorized target profile timezone, derives local dates and calls the existing exact financial function. It returns startDate/endDate, periodStart/periodEndExclusive and observedAt. Snapshot dates use those actual returned bounds. At `2026-10-01T20:30:00Z` Dubai is October 2; the service → actual repository → SQL regression selects September 26–October 2, retains October 2 income, and preserves USD. Existing support grants and recent-login policy remain in force. The integration fixture uses savepoints solely to preserve test rollback while executing the real repository SQL; capture storage is mocked to inspect the snapshot.
