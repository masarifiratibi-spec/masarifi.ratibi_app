## Decisions and behavior

- Overview values come from the response, including 0, 12 and 1234. Missing billing and HTTP-error telemetry stays null/unavailable, with unavailable regions rather than invented charts. Plan labels use the actual plan key; paid share uses actual counts.
- Registered profiles, new profiles in the reporting range, overlapping native-platform populations, unknown-platform users, registered devices and app versions come from stored records. Device presence is never an activity signal. Version distributions retain all devices with at most 24 individually named versions plus an other-versions group per OS.
- Import, AI and support sources have no reliable originating OS. Their real counts and import trend are explicitly global, including under an OS filter. Admin-support AI traffic is excluded.
- Native startup/foreground records one authenticated user/platform observation per UTC 15-minute bucket. The endpoint accepts only platform, refuses browser Origin, and requires an active profile and an owned, unrevoked native device bound to the authenticated Clerk session. The mobile helper captures/rechecks identity around registration and delivery. No content, screen names, device identifiers or client timestamps are stored in the activity table.
- Collection starts at migration execution, with no historical backfill. Reports return collection start, database observation time, reporting boundaries and timezone. Daily users are distinct users per configured reporting day; monthly users use a rolling 30 reporting days. Dates before collection have null points, and incomplete activity history is marked partial. Multiple devices and overlapping platforms deduplicate by user for totals. Retention is 120 days, enforced from the existing report-expiration worker polling path; profile deletion cascades observations.
- Support financial reports retain support-grant checks and use canonical confirmed, undeleted transaction effects with exact local start-inclusive/end-exclusive bounds. Snapshot/PDF currency follows currency_code and the currency catalog minor-unit scale, including mixed currencies. Existing public/mobile report response contracts remain unchanged.
- Overview, platform analytics and activity CSV exports capture actual dataset rows with dataset-specific columns and formula neutralization. Snapshot metadata retains observation boundaries. Audit mapping uses emitted security action names and distinguishes deletion requested/cancelled from completed records; includes role changes and support decisions.

## Local database verification and limits

Baseline-to-updated interfaces: existing `read_admin_report_counts(text,integer)` remains available, but the repository now calls new JSON-returning `read_admin_report_measurements(text,integer)`. Existing `read_admin_overview_activity(text,integer,integer,integer)` keeps its table-return signature; the event vocabulary is extended and mirrored in Admin Zod. Existing `read_supported_financial_report(text,date,date)` keeps its signature and support-grant admission, adding currencyCode/currencyMinorUnits/timezone/ledgerVersion metadata while preserving summaries. New private collection/bucket tables expose no raw grants; only the API can execute `record_mobile_activity(text)`, only the worker can execute `prune_mobile_activity()`, and Admin measurements still assert `admin.overview.read`. Public/mobile financial-report routes and schemas are unchanged.

The 13 live DB cases are: authenticated collection/dedup/no-history; unowned session denial; overview permission denial; support-grant denial; real audit request/cancel/completion/role/support mappings; timezone daily/rolling-30 membership plus retention; browser OS denial; revoked device denial; different-session denial; exact seven-day financial bounds/currency; bounded version distribution with preserved device sum; multiple-device/platform user dedup and unknown registrations; raw activity access denial.

All new SQL and live regressions ran only on the controller's isolated native PostgreSQL 18.6 database at port 55442. The existing service at 5432 was untouched. Baseline schema, official PGMQ SQL and minimal Storage tables came from the controller harness. This proves PostgreSQL function/role/RLS behavior locally; it does not claim target Supabase PostgreSQL 17, Storage HTTP, hosted Clerk, physical device, email/provider or deployment verification.

The harness initially recorded the newly created migration while it was still empty (150 historical migrations plus that empty candidate). Completed SQL was applied transactionally to this disposable database; iterative function updates were applied directly during RED/GREEN. The controller independently reported successful final-source replay on separate `admin_recovery_fresh` (all 151 nonempty sources) and `admin_recovery_upgrade` (historical 150 plus candidate) databases, with 13/13 new regressions passing on each. No historical tracked migration was edited.

No hosted mutation, deployment, live provider call or phone write occurred. Mobile activity uses existing authenticated API/device registration infrastructure. Operational retention depends on the existing report worker running. Collection measures native foreground observations, not arbitrary in-app interaction, sessions, or historical usage. Aggregate export captures current database observations; audit pagination is bounded to 10,000 records with an explicit limit error.
