# Quickstart: SPEC-010 Validation and Delivery

Run commands from `apps/mobile`. Store safe summaries in
`specs/010-frontend-quality/validation.md` and native artifacts under
`specs/010-frontend-quality/evidence/`.

## 1. Prerequisites

- Install the locked dependencies.
- Use a supported Node/npm environment and an Expo development build.
- Connect an Android test device with USB debugging for native validation.
- Use macOS/Xcode with an iOS simulator or device for iOS/VoiceOver validation.
- Use only disposable validation profiles when resetting scenarios.
- Never retain real financial values, credentials, authored messages, transcripts, assistant
  content, or participant identity in evidence.

## 2. Static and Architecture Gates

```powershell
npm run typecheck
npm run lint
npm run check:foundation
npm run check:design-system
npm run check:app-shell
npm run check:core-finance
npm run check:automatic-tracking
npm run check:voice-capture
npm run check:financial-planning
npm run check:reports
npm run check:assistant-notifications
npm run check:frontend-quality
node scripts/check-frontend-quality-boundaries.test.mjs
```

If `check:automatic-tracking` is not yet an existing script, the implementation task must either
add that focused ownership gate or document which existing tracking gate provides equivalent
coverage before the aggregate command is considered complete.

Expected: every command exits 0. The aggregate check reports each feature gate separately and
rejects direct SQLite/provider imports in UI, server-shaped Zustand data, secrets, sensitive logs/
analytics, raw colors/strings, unsupported iOS SMS claims, incompatible contracts, and unguarded
financial commands.

## 3. Focused Behavior and Persistence

Run focused suites created by the implementation tasks for:

```powershell
npx jest --runInBand src/services/contracts
npx jest --runInBand src/test-utils/frontend-quality-scenarios.test.ts
npx jest --runInBand src/storage/database.test.ts
npx jest --runInBand src/storage/core-finance-persistence.test.ts src/storage/financial-planning-persistence.test.ts src/storage/reports-persistence.test.ts
npx jest --runInBand src/features/transactions/SyncConflictScreen.test.tsx src/features/financial-planning/PlanningStates.test.tsx
npx jest --runInBand src/analytics
```

Expected:

- compatible provider replacement succeeds and incompatible major selection fails before use;
- concurrent same-operation calls invoke the owner once; restart replay returns the exact success;
- failed attempts retry with the same operation ID; no partial or duplicate financial effect;
- both conflict versions survive failure/restart and only an explicit valid choice resolves them;
- SQLite v1→v7 upgrade, reopen, rollback, uniqueness, and existing data preservation remain green;
- analytics payload/envelope are immutable and reject every forbidden field.

Use exact focused paths generated by tasks if ownership-specific files differ; record them in the
delivery ledger.

## 4. Scenario Catalog and Reset

Open the development validation selector or invoke its test seam. For every named profile in the
scenario contract:

1. select the disposable validation profile;
2. reset and seed the scenario;
3. capture the expected routes/states;
4. mutate one representative record when applicable;
5. reset and seed again;
6. compare observable initial records and states.

Expected: two clean runs are equivalent; relationships resolve; dense counts match; normal user
profiles refuse reset; no fixture requires hand-editing stored data.

## 5. Offline, Retry, and Conflict Journey

Validate manual entry, voice save, automatic capture, obligation payment, report operation,
assistant-confirmed action, notification action, subscription operation, privacy request, and
support submission as applicable:

1. disconnect before submit;
2. verify input/draft survives and status is pending or failed, never synchronized;
3. retry while still offline and verify no duplicate;
4. restore connectivity and retry using the same operation ID;
5. inject a competing later version;
6. verify both versions/effects remain visible and no automatic merge occurs;
7. cancel, then explicitly resolve; reopen and verify one final effect.

Expected: primary navigation and manual capture remain usable throughout; immutable history does
not refresh; only affected live projections invalidate after owner success.

## 6. Full Automated Regression

```powershell
npx jest --runInBand
npm run typecheck
npm run lint
```

Expected: all suites/tests pass with zero skipped or weakened required checks. Record exact suite/
test counts and all warnings. Investigate open handles and React state warnings rather than hiding
them.

## 7. Localization, Accessibility, and Visual Matrix

For representative sign-in, onboarding/tracking, Home, transaction add/detail/conflict, voice,
planning/obligation, reports, notifications, assistant/action, subscriptions, settings/privacy,
and support routes, validate:

| Dimension | Required cases |
|---|---|
| Language/direction | Arabic RTL, English LTR, mixed currency/date output |
| Theme | Light, dark, sufficient contrast |
| Size | 320×568 logical viewport, standard phone, large phone/tablet adaptation |
| Text/input | 200% text, long Arabic, keyboard open, validation correction |
| State | loading, empty, dense, partial, error, offline, denied, disabled, read-only, limit, conflict |
| Access | logical focus, name/role/state, 44×44 target, non-color status, reduced motion |
| Privacy | hidden values absent from visual and spoken labels |
| Overlays | safe areas, bottom sheets/dialogs, primary action remains reachable |

Expected: no missing key, hard-coded user string, clipped critical value/status/action, inaccessible
chart, focus trap, duplicate announcement, or direction error.

## 8. Privacy and Artifact Inspection

Use deterministic canary strings representing a secret, amount, account ID, transaction text,
SMS body, transcript, assistant question/answer, support text, and raw provider error. Exercise
analytics, logs, notification presentation, errors, tests, and evidence creation.

Expected:

- canaries do not appear in analytics, logs, screenshots/XML retained as evidence, or build config;
- events contain only allowlisted categorical/timing fields and cannot be mutated after creation;
- source/config scan finds no production key, service-role secret, direct production provider call,
  or push token request outside approved scope.

Record the scan command/pattern categories, not secret-looking values themselves.

## 9. Performance Measurement

Document OS, CPU/RAM summary, Node/runtime, device model, viewport, theme, locale, and fixture counts.
Warm once, then record at least 20 returning-shell runs and the dense-list tests.

```powershell
npx jest --runInBand <shell-performance-test>
npx jest --runInBand <transaction-dense-list-test> <notification-dense-list-test>
```

Expected:

- at least 19/20 shell runs show useful content under 2 seconds;
- 1,000-record lists show useful content under 2 seconds;
- fewer than 100 content rows mount;
- paging is stable and duplicate-free;
- delayed optional requests do not block navigation/manual capture;
- performance logs contain no protected fixture content.

## 10. Android Native Acceptance

On the connected development-build device, run from a clean disposable profile:

1. Arabic and English sign-in journeys.
2. Tracking education, skip, grant, deny, permanently deny, system-settings recovery.
3. Clear automatic event and uncertain review event.
4. Verify accounts, transactions, budgets, reports, obligations, notifications, and assistant agree.
5. Exercise in-app and phone notification foreground/background/cold responses.
6. Tap View, Edit, Undo, duplicate response, expired action, changed/deleted target, and locked action.
7. Verify unlock precedes revalidation and owner execution; retry produces one effect.
8. Exercise offline local save, retry, reconnect, and preserved conflict.
9. Repeat key screens in light/dark, small/large display, 200% text, hidden values, and TalkBack.

Expected: Android story completes with honest states, one financial effect, safe fallback, and no
sensitive notification/accessibility leakage.

## 11. iOS Native Acceptance

On macOS/Xcode:

1. Run Arabic and English sign-in.
2. Verify no direct-SMS promise, permission, or tracking action appears.
3. Complete manual and voice capture alternatives.
4. Verify the same downstream financial views, notification, assistant explanation, correction,
   offline retry, themes, 200% text, hidden values, and VoiceOver behavior.

If macOS/Xcode is unavailable, record the gate as blocked with the missing prerequisite. Do not
mark it passed from Android or automation. Closure then requires completion later or the defined
product-owner exception.

## 12. Participant Study

Recruit at least 12 participants: six Arabic and six English; at least four regular screen-reader
users with both languages represented. Assign the selected core task at 200% text using their
normal assistive navigation. Record anonymous completion without help and 1–5 clarity/trust/
recoverability ratings.

Expected: at least 11 of 12 complete without help and at least 11 of 12 rate the story 4 or 5.
Report aggregate results only. If the sample is incomplete, the gate is blocked—not estimated.

## 13. Closure Ledger

Create `validation.md` with one row per validation case and a final gate table. A release is ready
only when architecture, behavior, persistence, localization, accessibility, privacy, visual,
performance, Android, iOS, participant, and final end-to-end gates pass.

For a blocked required gate, closure is prohibited unless the product owner records:

- exact blocked gate and missing prerequisite;
- concrete risk;
- approver and accountable follow-up owner;
- expiry date;
- required follow-up evidence.

Any failed gate blocks closure without exception. Re-run relevant focused tests, full Jest,
typecheck, lint, boundaries, privacy, and performance after the last corrective change.
