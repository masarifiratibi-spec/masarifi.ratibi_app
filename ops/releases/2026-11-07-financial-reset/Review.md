# Financial reset release

This packet enables an owner to reset their personal financial history while keeping the same identity, financial accounts and selected settings. The compiled overlay derives from the running image of each affected service. No reset is submitted during rollout. Android 133 advertises the action after the state endpoint is available.

1. Reconcile the serving API, import, sync, planning, reports, engagement, assistant, voice and scoped privacy consumers. For each affected service record its image digest, compose file order, environment fingerprint, command, role and job allowlist. Retain its prior image and configuration for rollback. Compare each affected module with its before hash using build-overlay.py PACKAGE_DIRECTORY CONTAINER. Stop and qualify any actual baseline differences before switching traffic. Verify the candidate program boots with the appropriate worker role on an isolated fixture before replacing a container.
2. Apply the included SQL as one tracked Supabase migration, using the normal migration executor on project qcffvfbpzvpwcwxwjyro. Verify the new migration version and privileges, the scoped financial cleanup job and the existing privacy account deletion job. Applying the migration creates the capability without resetting any customer.
3. Roll the affected workers to the qualified candidate for each service, preserving runtime settings and job assignments. Extend only the dedicated privacy consumer's allowlist to privacy.account-delete,privacy.financial-reset-cleanup. Recheck consumer health and successful scheduled claims before replacing the customer API. Replace only the image in each existing Compose configuration. Check database/queue readiness, public TLS health, device and owner authorization, and cross-owner receipt isolation. Use only synthetic accounts for end-to-end financial writes.
4. Enable delivery of Android 133 once the API is ready. iOS uses the same route and server contract. The local iOS JavaScript export is available separately from a signed IPA. Monitor reset failures, cleanup age and retries without logging financial contents.

Rollback must keep the database generation fences in place. Withdraw the reset endpoint/card first, retain a matching cleanup consumer until pending file cleanup finishes, and use the recorded prior image for each affected service only after confirming it can still serve reset owners safely. A rollback cannot restore erased financial history. Keep existing account deletion functioning.

Verification used local disposable users, including a staff owner, two currencies, pending offline writes, stale and missing generation headers, externally stored objects and repeated requests. See the qualified SQL and mobile tests for the assertions.
