# Database repairs for the next production release

The mobile branches carry the same backend changes. Build once against the current production server image and preserve its existing operating overlays. The previously deployed N+1 migration is 20261121074801. The requested-PDF worker and migration 20261121095500 are part of the pending local bundle.

## Preparing one release

1. Check the production migration ledger, installed function hashes and enabled worker scopes against the release candidate. The Nov 20 routine-success suppression was previously recorded in production. The new completion migration supports that body and the earlier version in the mobile branches. Apply only missing, verified migration versions. Use the normal migration ledger lock and a separate transaction for each version.
2. Prepare the two concurrent retention indexes as documented in the [history and restore procedure](../2026-11-21-job-history/README.md). Apply the email and voice migrations before replacing either worker. Apply 101100, 101200, 101300 and 101400 before enabling retention, import reconciliation or the updated deletion worker. The 101400 migration retains the existing one-second scheduler poll and reads the active-run index before entering the expensive claim path.
3. Take the read-only inventory in `coverage.sql`. It lists the registered handler, scheduled time, last run and evidence of a running scoped worker for each job. Compare it with running container scopes and health. The Nov 21 snapshot had 45 overdue schedules out of 52 enabled. A specialized voice heartbeat and the requested-PDF delivery worker have independent health signals. Match each overdue key to the deployed feature contract before changing its scope. `notification.dispatch` requires particular attention because it may deliver pending user notifications.
4. Start one worker scoped to `operations.job-history-retain` as described in the retention procedure. Confirm a successful claim through that worker, then check the size of the live tables, archive growth, lock timeouts and API p95. Its 90-day minimum and archives apply to runs and attempts. The archive consumes database space. Rehearse a sample restore from backup.
5. Check which process drains the import changes. A healthy `tracking.reconcile` worker owns this in the application. `import.parse` does not reconcile existing items. Where this job is outside the active scope, use `activate-import-reconciliation.sql` under the maintenance login for a five-minute, eight-session SQL schedule. This runs only the reconciliation capability. Check the next completed run, the first marker ID and a sample capped at 1,001 rows over two cycles. Increasing marker age or a stationary oldest ID across successful cycles merits investigation. Recovery also visits a bounded page of historical IDs during due calls.
6. Prepare the receipt consumer only for the `report.delivery_succeeded` status/metrics contract. Check the queue name, PGMQ version, extension owners and the pg_cron database. As the existing authorized maintenance login, run `psql -X -v ON_ERROR_STOP=1 -1 -f install-receipts.sql` and then `psql -X -v ON_ERROR_STOP=1 -f index-receipts.sql` outside a transaction. On a failed concurrent build inspect the index definition and validity before retrying. Run `activate-receipts.sql` with `-1` as the same login. Its saved activation instant survives pause and resume. Each five-minute invocation handles up to 32 due messages and commits receipts, classification and queue archive together. SMTP sends stay with the existing report worker.
7. Check the first real cron runs using `receipt-health.sql` as the scheduling login. Verify a newly accepted test report, queue lag, issue count, current archive/attempts, voice heartbeat and the existing API routes before widening traffic. The age alert is ten minutes for the status receipt. Delivery latency is measured from the ready report until SMTP acceptance, separately from this bookkeeping. Compare top queries and P95 API latency during comparable traffic windows. Each enabled five-minute cron job adds up to 288 pg_cron run records per day when run logging is enabled. Include those tables in the site's existing monitoring and retention policy.

## Queue ownership and recovery

The forward publisher delivers envelopes to PGMQ. The receipt consumer records one SMTP acceptance per event ID and exposes the latest timestamp. Report generation, sending and retry continue to follow their authoritative report-attempt state. Financial changes, voice and notification delivery keep their existing domain owners. Operations completion history is authoritative in the run and attempt tables. Use the bounded event-type inventory before assigning any additional event family to a consumer.

A valid duplicate shares the receipt and moves to the queue archive. An invalid post-activation receipt is retained there with a matching `invalid_receipt` issue. A source waiting for publication is deferred for one minute for up to one day and then held live with an `unconfirmed_publication` issue. Pre-activation source messages stay live. Messages enqueued before activation and unrelated event types are outside the consumer's query. The publisher's existing Nov 19 forward boundary remains in force. To investigate, join issues to the live queue or archive by message ID in a private maintenance session. Keep payloads out of logs. Resolve the underlying source/contract before authorizing an individual retry.

To pause cron jobs, call `cron.unschedule('masarifi-report-delivery-receipts')` or `cron.unschedule('masarifi-import-reconciliation')` as their owner. Preserve the stored boundary, receipts, archives and import markers. Resume with the activation script and verify a real run. On mixed-version rollback, restore the previous application and stop dependent workers before considering a forward SQL correction. Keep the durable archive and reconciliation data available for diagnosis and recovery.

## Local qualification

`verify-completion.sql`, `verify-scoped-claims.sql` and `verify-receipts.sql` exercise real PostgreSQL routines with synthetic data. The completion script expects a migrated operations fixture with the retry-safe `sync-mutations.retry` registration. Wrap it in a rolled-back transaction. The receipt script expects a new, isolated platform-events queue with PGMQ 1.5.1, its new tables/index and an empty activation record. Execute it once with `psql -1 -v ON_ERROR_STOP=1` in the disposable database. It tests a pre-commit crash, duplicate delivery, malformed input, both forward boundaries and publication confirmed after the first queue read. The local receipt qualification used upstream PGMQ 1.5.1 SQL. It executed the stored cron command directly with a simulated catalog. Actual pg_cron background dispatch and production traffic are release checks.

The old backlog and other event families remain pending an owner and an explicit disposition. No historical replay is part of this release.
