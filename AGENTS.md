# Masarifi project instructions

Use [the maintained project guide](docs/project/README.md) and [release workflow](docs/project/release-workflow.md). The approved target is one permanent source branch, `main`, containing API, Admin and both mobile platforms. Implement changes on temporary `codex/<task>` branches from main and qualify both platforms when shared mobile code changes. During consolidation, `codex/unify-platforms-on-main` is the candidate; verify its acceptance receipt and actual merge before treating it as delivered. Historical operating/Play/iOS refs are recovery evidence, not default destinations for new work.

Check branch, upstream and full source SHA before editing. The canonical remote is `ratibi` for `masarifiratibi-spec/masarifi.ratibi_app`; do not push to an unrelated historical origin. Use platform files and build profiles for Android/Apple differences. Keep the additional assistant consent on Apple only and preserve its future-review comment. A shared change is not accepted until its relevant platform checks pass.

Read each app constitution for domain rules. Use live adapters in configured production profiles and fixtures only in explicit demo/test modes. Enforce owner/staff permissions on the server. Use disposable databases for migration tests. Never infer deployment from a branch, file timestamp or CI success.

Push and merge qualify source only. Server deployment, production migrations, OTA updates, signing and Store submission require a separate release instruction. Audit actual workflow/event conditions before changing CI or signing. Preserve historical dated receipts and unrelated dirty worktrees. Read [single-main inputs](docs/project/single-main-inputs.md), [acceptance](docs/project/single-main-acceptance.md), and [observed deployment versions](docs/project/deployed-versions.md).
